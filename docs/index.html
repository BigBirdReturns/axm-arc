What is an arc Source

This started as a guild-management game. It ended as something more honest: an engine for any group of agents facing structured challenges under constraint, with their interpersonal dynamics mechanically affecting outcomes. The first arc is fantasy. The second could be Karazhan, a startup's first year, a defense program's milestone cycle, or a hospital's staffing crisis. The engine doesn't care. It runs the simulation.

The artifact

An arc is a portable scenario

An arc is a single JSON file. It declares the domain: how many attributes, what they're called, which roles exist (if any), the tier structure, the resource economy, the progression chain, every challenge, every reward, every narrative event.

The engine knows nothing about the domain. It processes agents, attributes, challenges, and relationships. Load a different arc and you have a different simulation — same engine, same guarantees.

The arc is the contract. Schema validation at the trust boundary rejects bad data before it reaches the engine. If an arc passes validateArc(...), it will run.

This is the compilation thesis applied to play: declare the world once, simulate it forever, hand the file to someone else. A balance discussion becomes evidence, not anecdote. A replay is a seed, not a memory.

The engine

Four guarantees

An arc is portable because the engine that runs it is honest about what it promises. Four things hold; everything else is content.

Guarantee 01
Determinism
Given the same arc, the same starting organization, and the same seed, the engine produces the same run report. Same scores. Same loot rolls. Same drama triggers. Same narrative seed for the template renderer.
Seed derivation: hashSeed(orgSeed, cycle, challengeId) · covered by determinism tests in resolver + integration suites.
Guarantee 02
Schema validation
Arcs are validated at the trust boundary. Attribute weights must sum to 1.0. Drop rates are clamped to [0, 1]. Referenced attribute IDs must exist. The arc is either runnable or it throws — never half-correct.
Zod schema in src/engine/schema.ts · validateArc(input) returns a typed Arc or throws.
Guarantee 03
Content-free engine
No challenge name, no item, no attribute label is hard-coded in engine code. The engine processes arc data through pure functions. Swap arcs without touching a line. The first arc happens to be fantasy. The next one doesn't have to be.
Engine in src/engine/ · tutorial arc in src/arcs/ · no cross-imports from engine into arcs.
Guarantee 04
Offline-first save
Versioned save format. Maps serialize as arrays of pairs. Migrations are a typed dictionary. Loading a save against a different arc throws. Loading a save against a different engine version with no migration throws. Your decisions don't vanish on session end.
Save key axm-arc:save:v1 · localStorage today, IndexedDB-ready for larger states.

Why AXM cares about arcs. The AXM family is built on one thesis: portable, verifiable, traceable artifacts beat black-box runtimes. axm-chat applies it to conversations. axm-show applies it to drone choreography. axm-embodied applies it to forensic flight records. axm-arc applies it to simulated organizations.

The structural property in every case is the same. The interesting work happens at compile time (extract claims, define an arc, plan a show). The artifact is then portable, schema-validated, and queryable forever without further inference. The runtime is deterministic local math, not a network call.

What this buys you. A community can disagree about whether a Karazhan tuning is too forgiving and produce signed replay seeds to settle it. A research team can publish an arc representing a hypothesis about team dynamics and hand it to a reviewer. A training program can ship a scenario as a single file that runs the same way on every machine, offline, with no version drift.

An arc is the opposite of a balance patch you can't remember being applied.

Questions

Before you ask

Is this a game or an engine?

Both, deliberately. The engine is a generic organizational simulator: agents with attributes, relationships, stress, and morale, facing challenges under resource constraint. The first arc (The First Charter) is a small fantasy guild scenario that teaches the systems. The intended second arc is Karazhan — a faithful Burning Crusade Phase 1 raid tier. The intended third arc could be anything: a defense program's milestone cycle, a startup's first year, a hospital's staffing crisis. Same engine, different domain.

Why deterministic? Doesn't that make outcomes feel scripted?

Determinism is about reproducibility from the same starting state, not about removing variance. With the same seed, same arc, same roster, you get the same run. Change any input and the run changes. What determinism buys: replayable interesting runs, regression tests when you change the resolver, the ability to publish a run as evidence, and the ability for two people to argue about a balance decision with the same data.

Can I write my own arc?

Yes. Arcs are JSON. The schema is defined in src/engine/schema.ts with explanatory errors. Look at src/arcs/first-charter.ts for a worked example with 4 attributes, 3 roles, 3 tiers, 6 challenges, and a small item set. The schema enforces correctness (weights sum to 1.0, referenced IDs exist, drop rates in [0, 1]) so a malformed arc fails loudly at load.

Does this need the AXM Protocol installed?

Not today. axm-arc runs standalone. It is TypeScript / React / Node — no Python sidecar, no shard emission, no key management. The protocol-membership claim is about the design principles (portable artifact, deterministic runtime, no inference at query time) that arcs honor. Full integration — emitting arcs as signed Genesis shards — is on the roadmap, not in the ship.

Will arcs ever be cryptographically signed?

That's the plan. The arc bytes are already canonical (the JSON shape is stable; engine version is pinned in meta). What's missing is the Merkle root, the signature, and the verifier. Once an arc is signed, "this is the same arc the author published" becomes a one-line local check. A community registry on top of that becomes possible.

How is this different from a tabletop sim or Twine?

Tabletop is human-resolved. Twine is graph-of-passages narrative. axm-arc is a mechanical resolver: a player doesn't make choices in a fight, they assign agents and read the report. The interpersonal dynamics — stress cascades, drama events, precedent violations — are first-class mechanics with stat effects. The game is the audit, not the play.

What does AXM stand for?

Agnostic, Extensible, Modular — for the protocol family. Any extractor, any domain, any deployment. For axm-arc specifically: any arc, any organization, any engine version that satisfies the arc's engineVersion floor.
