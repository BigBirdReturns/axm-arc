Abstract

An arc is a portable JSON scenario that defines a domain (agents, attributes, roles, challenges, rewards, narrative). The engine runs it the same way every time, with the same seed. No inference cost, no API, no network. The player assigns agents to challenges. The engine resolves them. The drama is mechanical, not decorative.

IWhat is an arc

An arc is a single JSON file that declares a complete organizational scenario: how many attributes exist, what roles agents can fill, the tier structure, challenges with mechanic checks and difficulty thresholds, reward tables with drop rates, narrative events, and progression chains. The engine knows nothing about the domain. It processes agents, attributes, and relationships. Load a different arc and you have a different world.

The first arc is fantasy. A guild of six agents takes on contracts of increasing difficulty. The second could be Karazhan — the most beloved raid instance in MMO history, faithfully modeled with attunement chains and a 10-to-25 expansion moment. The third could be a defense program office, a startup's first year, or a hospital's staffing crisis. Same engine. Different domain. Same guarantees.

The arc is the contract. If it passes validateArc(), it will run.

IIIThe engine

The player assigns agents to challenges. The engine resolves them deterministically and returns a structured report. The player never directly controls an agent in a challenge. They manage — assigning, equipping, resting, resolving drama — and read what happened.

Every agent has primary attributes, hidden attributes (loyalty, ambition, volatility, leadership), personality traits with mechanical effects, morale, stress, and a relationship web with every other agent. These aren't flavor text. When stress hits 10, a resolution event fires: 75% chance of affliction (Resentful, Fearful, Defiant, Reckless, Withdrawn), 25% chance of Resolve — the clutch moment that lifts the team. An afflicted agent generates barks that stress nearby agents, creating cascade risk. This is the organizational death spiral. It happens in real guilds. It happens in real companies.

Reward decisions feed the relationship system. Every allocation is logged in a precedent store. Violate the established pattern and high-ambition agents notice. The player's decisions teach the organization what to expect — and violations of those expectations cost more than the initial decision would have.

The drama has consequences because the drama has stat effects. Flavor text without mechanical weight is not a consequence.

VIFAQ

Is this a game or an engine?

Both. The engine is a generic organizational simulator. The first arc is a fantasy guild scenario. The second could model any domain: defense programs, startups, hospitals, raid tiers. Same engine, different arc file.

Why deterministic?

Reproducibility. Same seed, same arc, same roster = same run. Change any input and the run changes. This means replayable runs, regression tests when you change the resolver, and balance discussions backed by evidence instead of memory.

Can I write my own arc?

Yes. Arcs are JSON. The schema is in src/engine/schema.ts. Look at src/arcs/first-charter.ts for a worked example. The schema enforces correctness — weights sum to 1.0, referenced IDs exist, drop rates in [0, 1] — so malformed arcs fail at load, not at runtime.

Does this need the AXM Protocol?

Not today. axm-arc runs standalone — TypeScript, React, Node, no Python, no shard emission. The design principles (portable artifact, deterministic runtime, no inference at query time) align with the AXM family. Full Genesis integration is on the roadmap.

What does AXM stand for?

Agnostic, Extensible, Modular. Any extractor, any domain, any deployment. For axm-arc: any arc, any organization, any engine version that satisfies the arc's engineVersion floor.

Final note

The arc is the contract.
The engine is the audit.

Every decision the player makes — who to assign, who to reward, who to bench — is logged, weighted, and fed back into the organization's dynamics. The precedent store remembers what you taught the team to expect. The stress system remembers who you pushed too hard. The relationship web remembers who you put next to whom.

Swap "guild" for "program office" and "raid boss" for "contract deliverable" and you are modeling any organization facing structured challenges under resource constraints with imperfect information about its own people.

The game is the proof of concept.
The engine is the product.
